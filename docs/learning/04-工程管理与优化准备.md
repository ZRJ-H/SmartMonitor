# 工程管理、真实经验与后续优化

## 一、从“读代码”升级到“管理项目”

日常盯住五件事：
1. 要求：这次改动解决什么用户问题，验收条件是什么。
2. 状态：当前分支/提交、工作树是否干净、哪些验收仍开放。
3. 风险：涉及数据库、线程、文件还是仅 UI；失败怎样恢复。
4. 证据：测试和日志对应哪个代码版本。
5. 交付：别人能否按说明构建、安装、运行并复现结果。

建议每个任务保持一个小闭环：
问题记录 → 复现/基线 → 最小设计 → 实现 → 定向测试 → 全量门禁 → 提交 → 更新验收。
不是每次都必须写很多文档；一条清晰任务记录胜过一句“优化了一下”。

## 二、工程工具各自解决什么

| 工具或产物 | 解决的问题 | 常见误解 |
| --- | --- | --- |
| .pro / .pri / qmake | 声明编译输入和依赖、生成构建规则 | 文件放进目录就会编译 |
| build-and-test.ps1 | 固定工具链、隔离遗留生成文件、回归 | Qt Creator 能点运行就算可重建 |
| source-fingerprint.ps1 | 标识实际构建输入 | 提交号能唯一描述含未提交改动的构建 |
| latest.json / runs | 记录状态、源码指纹和 EXE hash | 上次绿色报告代表现在也绿色 |
| package-release.ps1 | 收集匹配的运行库并核对产物 | 复制一个 exe 到别处就能运行 |
| SQL 迁移 | 用可复核方式改变已有结构 | 在查询函数里随时建表比较方便 |
| SQL 备份与媒体备份 | 提供恢复材料 | 有 SQL 文件就保住了视频本体 |
| observe-runtime.ps1 | 收集运行中的内存/CPU/句柄等 | 启动观察脚本就是七天验收完成 |

自动测试能证明已覆盖的行为，不能替代真实摄像头、实际模型和干净机器验证。
当前源码指纹也包含文档，所以改手册后跳过构建打包可能被拒绝；按脚本重新验证即可。

本机维护命令使用 PowerShell 7。此次用旧 powershell.exe 调用时，
Get-FileHash 模块未成功加载；备份阶段停止，迁移尚未开始。
换成已验证的 PowerShell 7 后完成。这是“先确认执行环境”的真实案例，不能推广为所有 PowerShell 5 都不支持该命令。

## 三、本项目可学习的四次真实排障

| 现象 | 根因 | 修复与证据 | 可迁移的经验 |
| --- | --- | --- | --- |
| 构建阶段 moc 异常 | 源目录遗留生成文件影响构建依赖 | 按受控输入镜像再构建 | 区分源码、生成物和依赖 |
| 两秒采样得到约 0.3 秒视频 | 固定 FPS 按帧数定义时间 | 补帧并检验实际解码时长 | 指标单位和时间轴要一致 |
| 事件重试总失败 | JPG 已落盘但 SQL 回滚，同名冲突 | 校验内容后接纳孤立事件图 | 多资源操作要设计中间状态 |
| 后面的待办永远恢复不了 | 每次只尝试字典序前 20 个坏条目 | 持久化轮转游标 | 限流还要考虑公平性 |
| 十万条事件筛选超过 3 秒 | 关联路径缺索引 | 隔离库补索引后最高约 724 ms | 用真实数据规模与执行计划验证 |

最后一项测量包含 mysql 客户端启动和连接，不能把它当成纯服务器执行耗时。
发布包最初 offscreen 检查失败而 Windows 插件启动成功，也说明“测试环境”和“目标运行环境”必须分别识别。

## 四、性能优化先准备可比较的实验

固定这些条件：同一提交、同一电脑、电源模式、视频文件、分辨率、通道数、
检测开关/模型、记录时长和磁盘位置。记录预热与重复次数。

建议分组（这是待执行方案，不是已经有的结果）：
- 单路预览、不检测；
- 四路预览与录像、不检测；
- 单路预览与录像、启用检测；
- 四路运行时打开图片查询或回放。

| 指标 | 怎样理解 | 当前观察脚本是否直接提供 |
| --- | --- | --- |
| CPU 累计秒 | 要取差分并除墙钟时长，必要时按逻辑核数归一化 | 是 |
| privateBytes / workingSet | 观察趋势，区分缓存增长和持续泄漏 | 是 |
| 采集到显示的 P95 延迟 | 需要在关键位置加单调时间戳 | 否 |
| 有效采集/编码 FPS | 需要独立计数器，不能从定时器配置推断 | 否 |
| 队列积压 | 统计生产与消费差或显式有界队列 | 否 |
| 查询耗时 | 区分连接、SQL、取数、缩略图解码与界面填充 | 否 |
| 视频/图片正确性 | 解码、时长、关联、偏移和重复记录检查 | 否 |

QElapsedTimer 用于同一运行中的间隔测量；QDateTime 用于可读业务时间。
不能用用户可调整的墙上时间直接替代所有性能测量。

## 五、值得验证的瓶颈假设

以下是源码能提示的方向，尚不能当作结论：

1. 推理位于 MonitorTask 采集线程，慢推理是否拖慢采集。
2. 每帧深复制、颜色转换和 GUI 缩放各占多少时间。
3. RecordTask 消费慢时，队列是否积压到高延迟。
4. MediaRecoveryService、图片写入、SQL 位于 GUI 接收链，是否造成操作停顿。
5. OFFSET 深分页是否随页数明显变慢，是否值得改游标分页。
6. SQLite 测试通过的查询在 MySQL、大量数据和不同索引下是否仍合适。

每个假设先测再改。吞吐更高但延迟更差，或速度提高却丢失三图关联，都不算成功优化。

## 六、架构优化的候选顺序

当前边界不完美：主窗口较重、部分 SQL 在 EventService 中、数据库单例仍被直接依赖。
保留这些事实，不把现状美化成完整的“标准 MVC”。

| 候选拆分 | 动机 | 改动前必须具备的保护 |
| --- | --- | --- |
| PlaybackController | 从主窗口拆出播放器状态与就绪定位 | 同源跳转、越界、文件丢失、退出权限测试 |
| ChannelRuntimeCoordinator | 统一启动、停止、配置应用和线程收尾 | 四路独立失败、重启、封口和退出测试 |
| EventRepository | 将事件 SQL 与媒体业务分开 | MySQL 事务/外键、幂等、半失败恢复测试 |
| 异步媒体持久化 | 减少 GUI 被磁盘/SQL 阻塞 | 有界队列、独立线程数据库连接、退出等待与重试顺序 |
| 统一配置入口 | 减少兼容读取分散 | 两套键优先级、相对路径、保存失败不应用的测试 |

这些是未来拟议类名，并不是仓库里已经存在的文件。
拆类数量增加本身没有价值；要减少某个可描述的耦合或改变的风险。
不要把 GUI 线程创建的 QSqlDatabase 句柄直接拿去其他线程执行 SQL。

## 七、进入优化阶段的门槛

你能独立解释三条业务链，做过至少三个可验证的修改，
并能拿出一份固定输入下的性能基线，就可以选择一个优化点。
推荐一次只改一种因素，保留前后运行条件、原始样本和回退提交。

优化提案只需一页：
- 现象和用户影响；
- 数据与复现步骤；
- 根因假设和反证方法；
- 候选方案、风险和边界；
- 验收指标；
- 回退方式。

结项中的真实模型、设备、干净安装和七天观察仍独立跟踪；
学习完成、功能实现、项目验收是三种不同状态。
