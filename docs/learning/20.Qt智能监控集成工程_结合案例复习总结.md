## 一、案例一：应用启动、页面切换和生命周期

**需求：**主页面和登录页面能够切换，退出时释放后台任务和数据库。

**入口：**[main.cpp](C:/QtProjects/day20_smart_monitor/main.cpp:1) → [manager/windowmanager.cpp](C:/QtProjects/day20_smart_monitor/manager/windowmanager.cpp:1) →
[view/mainwidget.cpp](C:/QtProjects/day20_smart_monitor/view/mainwidget.cpp:61)。

main 创建 QApplication。WindowManager 单例持有两个窗口，并接收登录结果；
MainWidget 持有页面、会话和线程对象。
主窗口初始化先创建控件、连接信号并加载配置和管理页面，再创建 Worker、自动启动配置完整的通道。
初次读代码时跳过 init_style 的大段 QSS，先抓构造、init_connect 和退出。

**状态与失败：**登录窗口隐藏不等于销毁；主窗口隐藏不等于停止采集。
退出先停止采集，再封口录像并接收保存通知，之后退出线程，最后释放数据库。
后台采集卡住时能否及时退出还需要实测，不能只从调用 quit 就推断必定成功。

**工程知识：**QApplication/顶层窗口有明确生命周期；单例便于访问，但增加全局依赖。
MainWidget 是当前主要协调点，不能把文件夹分层直接当作职责完全分离的证据。

**自测：**若在删除主窗口之前先释放数据库，哪个收尾环节可能受影响？

## 二、案例二：登录规则、业务结果和访问权限

**需求：**检查输入、核对账户、限制连续失败；后台监控随程序启动持续运行；查看画面和操作必须先登录。退出登录清空画面，关闭整个程序才停止后台任务（2026-09-24 需求澄清）。

**入口：**[view/loginwidget.cpp](C:/QtProjects/day20_smart_monitor/view/loginwidget.cpp:1) →
[service/userservice.cpp](C:/QtProjects/day20_smart_monitor/service/userservice.cpp:13) →
[model/usermodel.cpp](C:/QtProjects/day20_smart_monitor/model/usermodel.cpp:1)；权限见 [service/authsession.cpp](C:/QtProjects/day20_smart_monitor/service/authsession.cpp:1)。

AuthPolicy 管输入格式，LoginThrottle 管失败计数/锁定；
UserService 组织校验、查询和更新登录时间，返回 LoginResult。
登录成功把 userId 和 userName 传给 WindowManager，再写入 MainWidget 的 AuthSession。

**为什么返回结构体：**“错密码”“数据库故障”“暂时锁定”不是同一种失败。
如果只返回 false，界面无法给出正确处理。

**权限如何落地：**受限入口调用 require_permission；退出后清空播放器来源和当前录像，
禁用图片/日志管理页。系统自动事件使用空管理员身份，不冒充当前登录用户。

**现有取舍：**失败次数是进程内状态，重启不持久保留；密码校验仍是课程兼容的 MD5 路径，
不能将它描述为现代生产级密码方案。安全升级需单独设计数据迁移，不在本轮学习中直接更换。

**证据：**[tests/tst_day2_auth.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_day2_auth.cpp:1)。
**自测：**数据库断开为什么不能当成“密码又错了一次”？

## 三、案例三：四路配置和保存后应用

**需求：**每路配置摄像头/文件和名称，存储目录与采集间隔重启后仍有效。

**入口：**[service/channelconfigpolicy.cpp](C:/QtProjects/day20_smart_monitor/service/channelconfigpolicy.cpp:1)、

~~~text
控件里的候选值
~~~

**失败行为：**保存失败不能让正在运行的任务使用半套新配置。
但“数据库事务提交”和“四路线程全部成功重启”不是一个原子事务；后者仍可能遇到设备不可用。

**架构现状：**ConfigModel 与 SystemConfigModel 并存，主窗口还有部分配置读取逻辑，
这是兼容整合后的现状。将读取和应用策略统一，是以后可评估的重构。

## 四、案例四：采集、节拍和实时显示

**需求：**四路独立读取，文件循环播放，显示不直接阻塞主线程。

**入口：**[service/monitortask.cpp](C:/QtProjects/day20_smart_monitor/service/monitortask.cpp:1)、
[service/capturecadence.cpp](C:/QtProjects/day20_smart_monitor/service/capturecadence.cpp:1)、[service/frameratelimiter.cpp](C:/QtProjects/day20_smart_monitor/service/frameratelimiter.cpp:1)。

MonitorTask 在采集线程使用 QTimer 驱动 captureNextFrame。
CaptureCadence 根据源 FPS 和目标 FPS 计算读取步长；文件源可跳过一些帧来维持播放速度。
FrameRateLimiter 控制发出帧的频率。
配置采集间隔会限制输出速率，但当前还有 12 FPS 上限；填 40 ms 不等于必定输出 25 FPS。

显示分支：frameReady → MainWidget::display_frame → BGR/RGB 转换 → QImage →
QPixmap 缩放 → VideoLabel。预览用 Qt GUI 对象在主线程显示。

**选择理由：**节拍、限流和采集 IO 分开后，前两者能用纯逻辑测试；
不能把它们混成“多开线程就会变快”。

**失败行为：**打不开数据源会报告所属通道；读取失败会停止。
缺失输入、短 MP4 循环、停止后的状态要分别测试。

**证据：**[tests/tst_day3_monitor_task.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_day3_monitor_task.cpp:1)、[tests/tst_preview_performance.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_preview_performance.cpp:1)。
**自测：**仅把定时器间隔改小，为什么可能增加队列延迟而不是提高有效 FPS？

## 五、案例五：普通录像、封口与时间轴

**需求：**按配置时长分段，文件可解码，不因慢帧把实际两秒压缩成零点几秒。

**入口：**[service/recordtask.cpp](C:/QtProjects/day20_smart_monitor/service/recordtask.cpp:1)、[service/recordingsegment.cpp](C:/QtProjects/day20_smart_monitor/service/recordingsegment.cpp:1)。

~~~text
sourceReady → configure（目录、通道、FPS、分段）
frameReady → saveFrame
  → 到期时 closeSegment
  → 必要时 openWriter
  → 按编码帧序号补齐时间间隙
  → 写当前帧
closeSegment → release编码器 → 检查文件 → 发出Video元数据
~~~

RecordingSegment 管文件名、时间、滚动判断；RecordTask 管 VideoWriter 和真实 IO。
编码尝试 avc1，失败回退 mp4v；分辨率保持在约 1280×720 内并取偶数尺寸。
FPS 上限为 10，还受有效源 FPS 限制。

**重要公式：**固定 FPS 视频的位置约为“已写帧数 ÷ FPS”。
只有三帧、10 FPS 的视频约 0.3 秒；即使采集这三帧用了两秒，也不会自动变成两秒视频。
当前用最后观察到的帧补时间空档，图片偏移按真实写入帧号计算。
补帧使视频出现停留画面，并没有恢复漏掉的真实运动；这是明确的取舍。

**真实故障经验：**同一秒普通段和事件段可能重名；现有文件存在时加后缀，避免覆盖。
只检查 QFile::exists 不够，还检查可解码和时长。

**证据：**[tests/tst_recordtask_event.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_recordtask_event.cpp:1)。
**自测：**为什么写完一帧不能立即把整个录像标成“已完成可回放”？

## 六、案例六：检测到人 → 事件段 → 三图

**需求：**单画面选中的通道检测到人后，形成独立事件视频和三张关联图片。

**入口：**[service/monitortask.cpp](C:/QtProjects/day20_smart_monitor/service/monitortask.cpp:116) →
[view/mainwidget.cpp](C:/QtProjects/day20_smart_monitor/view/mainwidget.cpp:1215) →
[service/recordtask.cpp](C:/QtProjects/day20_smart_monitor/service/recordtask.cpp:143) →
[service/eventrecordingstate.h](C:/QtProjects/day20_smart_monitor/service/eventrecordingstate.h:1)。

当前 DNN 推理仍在该路采集线程，采样间隔约 500 ms；不是独立推理池。
源码按特定 YOLO 输出形状解释 person 分数，不代表任何 ONNX 都兼容。

状态规则：
- beginEvent 先封口普通段，事件段目标约 60 秒。
- 活跃事件期间重复 begin 不重启、不延长。
- EventRecordingState 在收到满足阈值的帧时依次取三张，阈值为 0/1000/2000 ms。
- 提前停止标记 interrupted，不伪装成完整事件。
- 四画面停止新检测；已经开始的事件录制仍由 RecordTask 状态管理。

“阈值为一秒”不保证相机恰在那一毫秒提供帧；偏移应记录实际编码位置。
MonitorTask 的检测活动标志、冷却逻辑，与 RecordTask 的录像活动状态是两套状态。
持续有人不会简单地“每一分钟必定生成新事件”；要根据消失、重入和冷却判断。

**证据：**[tests/tst_event_recording.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_event_recording.cpp:1)。
**自测：**把检测信号直接当作“事件保存成功”，缺了哪些步骤？

## 七、案例七：跨文件和数据库的可靠保存

**需求：**文件已经生成但数据库暂时失败时，可以重试，并保持媒体关联正确。

**入口：**[service/mediarecoveryservice.cpp](C:/QtProjects/day20_smart_monitor/service/mediarecoveryservice.cpp:1)、[service/eventservice.cpp](C:/QtProjects/day20_smart_monitor/service/eventservice.cpp:1)、
[service/imageservice.cpp](C:/QtProjects/day20_smart_monitor/service/imageservice.cpp:1)。

~~~text
录像封口
  → QSaveFile写待恢复JSON（含视频信息、事件采样帧及偏移）
  → 普通：VideoService → VideoModel
  → 事件：EventService提交事件/录像/映射 → ImageService保存三图
  → 成功删除待办；失败保留
下一轮 replay → 轮转遍历待办 → 再次尝试
~~~

恢复目录固定在应用数据目录，不跟随录像目录切换。
QSaveFile 的原子提交只是一个文件操作，不是覆盖 SQL 和媒体文件的分布式事务。

表间关系：
- video.id：录像 ID。
- exception_log.id：事件 ID。
- event_media_link：通过 event_key 关联这两个 ID。
- feature_image：引用事件、录像并记录 video_offset_ms。
- monitor_event：保留既有查询兼容，不能把其 ID 当成 exception_log ID。

**幂等的边界：**重复业务键不会重复建立完整事件，不等于任意损坏都能自动修复。
图片已命名而 SQL 还没提交时崩溃，重试只接纳编码内容完全相同的事件 JPG。
20 个坏清单不能挡住第 21 个好清单，因此轮转游标持久化。

**尚有边界：**当前恢复针对已封口并成功写出清单的媒体；
断电造成未封口 MP4 损坏、数据库连接半断开状态、删除期间崩溃都需要额外验证。
这轮只读讲解不顺带改变这些业务行为。

**架构现状：**EventService 内直接包含 SQL 事务，Model/Service 分界并不彻底。
后续可以抽出事件持久化层，但先用现有幂等/失败用例保护行为。

**证据：**[tests/tst_media_recovery.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_media_recovery.cpp:1)、
[tests/tst_day7_day8_regressions.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_day7_day8_regressions.cpp:1)、[tests/tst_mysql_integration.cpp](C:/QtProjects/day20_smart_monitor/tests/tst_mysql_integration.cpp:1)。
**自测：**SQL rollback 能否自动删除磁盘上已经生成的 JPG？为什么？

## 八、案例八：图片、查询和真实回放

**需求：**按条件查询图片，九宫格查看、放大、导出、删除，再跳到对应录像位置。

**入口：**[view/imagepage.cpp](C:/QtProjects/day20_smart_monitor/view/imagepage.cpp:1)、[model/imagemodel.cpp](C:/QtProjects/day20_smart_monitor/model/imagemodel.cpp:1)、

1. 一个普通帧如何同时显示和录像。
2. 一个事件如何拥有自己的视频与三张图。

能提出证据和可回退实验，才进入性能或架构优化阶段。
