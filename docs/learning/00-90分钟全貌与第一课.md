## 一、先用一句话解释项目

这是一个 Qt 桌面监控系统：从摄像头或本地视频读取画面，实时显示并分段录像；
选定单画面时可做人形检测，把事件录像、三张图片和日志关联起来，再查询和回放。

数据库主要存索引、配置、用户和关联信息。MP4/JPG 本体在文件系统里。
数据库保存成功、文件保存成功、视频能解码，是三个需要分别验证的事实。

## 三、你真正需要记住的地图

~~~mermaid
flowchart TD
  Entry[main / QApplication] --> Windows[WindowManager]
  Windows --> UI[MainWidget / GUI线程]
  UI --> Capture[MonitorTask × 4 / 采集线程]
  Capture -->|frameReady| Display[display_frame / GUI线程]
  Capture -->|frameReady| Record[RecordTask × 4 / 录像线程]
  Record -->|封口结果| Recovery[MediaRecoveryService / 当前GUI线程]
  Recovery -->|普通录像| Video[VideoService / VideoModel]
  Recovery -->|事件| Event[EventService / ImageService]
  Video --> DB[(MySQL 元数据)]
  Event --> DB
  Record --> Files[MP4 文件]
  Event --> Images[JPG 文件]
~~~

这只是应用自己创建的线程；Qt 多媒体、OpenCV 后端可能还会创建内部线程。
图中“恢复服务在 GUI 线程”是当前事实，也是以后分析卡顿的重要线索。

目录不是抽象名词：
- manager：窗口切换和生命周期。
- view：控件、输入、显示、页面之间的连接；MainWidget 还承担较多业务调度。
- service：业务规则、采集、录像、恢复等，不是每个 Service 都有线程。
- model：数据对象和数据库访问；这里的 Model 不等同于 QAbstractItemModel。
- util：数据库连接、验证码等支撑。
- database / tests / scripts：结构迁移、验证和工程工具。

## 四、第一课：只跟一帧画面走

先打开 [main.cpp](C:/QtProjects/day20_smart_monitor/main.cpp:1)。`QApplication app(argc, argv)` 建立 Qt 应用环境；
`app.exec()` 进入事件循环，等待鼠标、定时器、队列调用等事件。
事件循环是“不断处理到来的工作”，不能在它所在的线程里长时间卡住。

接着读 [manager/windowmanager.cpp](C:/QtProjects/day20_smart_monitor/manager/windowmanager.cpp:25)：
构造主窗口和登录窗口，连接它们的信号。窗口互相切换由 WindowManager 管理。
`main` 退出前先释放窗口，再释放数据库，避免窗口析构还需要数据库而连接已经被销毁。

现在只读 [view/mainwidget.cpp](C:/QtProjects/day20_smart_monitor/view/mainwidget.cpp:969)。
每个通道创建一个采集 Worker 和一个录像 Worker，并分别移入 QThread。
最关键的两条连接如下（省略循环外上下文，属于实际代码摘录）：

~~~cpp
connect(monitor_tasks_[i], &MonitorTask::frameReady,
        this, &MainWidget::display_frame, Qt::QueuedConnection);
connect(monitor_tasks_[i], &MonitorTask::frameReady,
        record_tasks_[i], &RecordTask::saveFrame, Qt::QueuedConnection);
~~~

逐项读：
1. `monitor_tasks_[i]` 是通知的发送对象。
2. `&MonitorTask::frameReady` 是信号的成员函数指针，不是现在调用函数。
3. 接收者分别是主窗口、录像任务。
4. 队列连接把调用安排到接收对象所属线程；不是让采集函数直接操作控件。

再读 [service/monitortask.cpp](C:/QtProjects/day20_smart_monitor/service/monitortask.cpp:203)：
`frame.clone()` 创建独立像素副本后发出去。跨线程的任务稍后才处理；
不能让它依赖即将被复用的采集缓冲区。单纯复制一个 cv::Mat 头部通常仍共享像素数据。

最后分别读 [view/mainwidget.cpp](C:/QtProjects/day20_smart_monitor/view/mainwidget.cpp:1448) 和
[service/recordtask.cpp](C:/QtProjects/day20_smart_monitor/service/recordtask.cpp:78)：
显示链把 BGR 转 RGB，再用 QImage/QPixmap 显示；
录像链处理编码尺寸、节拍和段状态，然后写视频。
它们接收到同一轮采集结果，但职责和运行线程不同。

## 五、第一课自测

先不展开答案，用自己的话回答：

1. 录像正在写磁盘时，为什么主窗口通常还可以响应按钮？
2. frameReady 同时连到两处，是否意味着 GUI 调用 saveFrame？
3. 把 `task->startCapture(config)` 直接写在按钮槽里，Worker 就一定在后台执行吗？

<details>
<summary>核对思路</summary>

1. 编码任务位于独立录像线程，主线程事件循环可以继续处理界面；这不保证所有场景都不卡，主线程 SQL/图片写入仍可能耗时。
2. 不是。两个队列连接分别安排到两个接收线程；不要把连接列表误读成串行调用。
3. 不一定。普通 C++ 函数调用在调用者线程同步执行；moveToThread 不会自动改写普通调用。实际 start_channel 用 invokeMethod 的队列调用。

</details>
