# 四路检测性能与本地文件事件索引修复计划

日期：2026-09-25。状态：已进入实施，变更与实际证据见 [实施验证](verification/gpu-recording-2026-09-25.md)。以下保留原始设计背景，实际路线调整以该验证记录为准。

## 1. 已确认的目标与边界

用户选择：本地视频保留原文件，只保存去重后的事件时间点与截图，回放定位原视频。

- 文件循环播放不产生普通 MP4 或事件 MP4；同一内容、同一分析配置复用事件与截图。
- 摄像头是真实不断变化的数据源，不能套用本地文件去重规则。第一阶段保持现有摄像头连续录像与事件保存行为。
- 保留真实 MonitorTask / RecordTask / QMediaPlayer 链路；不更换 YOLO 模型来规避问题。
- 首先解除 GUI 存储阻塞，并验证 GPU 后端；硬件加速不代替线程与存储改造。
- 不清理历史录像、图片或原视频；不迁移生产数据库。迁移脚本和隔离验证完成后，生产执行按 AGENTS.md 单独确认具体结构变更。

## 2. 现场证据

- main.cpp 已设置 OpenCV 计算线程上限 4。
- service/monitortask.cpp 已使用独立检测线程、每路一个在途任务、至少 500 ms 间隔；预览与录像有最新帧信箱。
- service/detectionworker.h 强制 OpenCV CPU 后端，每路独立加载 640×640 ONNX 模型。
- view/mainwidget.cpp 的 on_source_ready 没有区分文件/摄像头，均配置 RecordTask。RecordTask 收到帧就写普通段，没有检测到人也持续录像。
- MonitorTask 到 EOF 自动回首；下游帧没有携带文件身份、源时间戳或循环代次。事件键含当前系统时间，无法识别同一源片段的重播。
- RecordTask 事件段固定约 60 秒。短文件循环可被重复编码进一个事件段；仅延长触发冷却不能解决普通录像与重复内容问题。
- MainWidget 事件封口回调同步执行 PNG 编码、Base64/JSON、磁盘写入、解码和 SQL；每分钟恢复也在 GUI 线程执行。
- 当前性能测试为纯色 MJPEG 素材，预热 1.5 秒、测量 4 秒；不能覆盖真实人形触发及事件封口负载。

GPU 探测结果：

- NVIDIA GeForce RTX 4060 Laptop GPU；驱动 610.47；nvidia-smi 报告显存 8188 MiB。
- 当前工具链 Qt 6.11.2 / MinGW 13.1 / OpenCV 4.14。
- E:/opencv/build/CMakeCache.txt：WITH_CUDA=OFF，OPENCV_DNN_CUDA=OFF。
- 使用项目相同 MinGW、OpenCV 头文件和 DLL 编译并运行临时 C++ 探针，实际输出 OpenCV=4.14.0、CUDA_targets=0。
- 结论：显卡可识别，但现有 OpenCV DLL 不能直接使用 CUDA DNN。尚未执行 GPU 模型推理，不能报告 GPU 提速成功。

## 3. 新的数据流

| 数据源 | 预览 | 分析 | 媒体保存 | 回放 |
| --- | --- | --- | --- | --- |
| 本地文件 | 可无限循环 | 对内容和分析配置建立可恢复的一次分析任务 | 原视频引用、事件区间、按去重后的异常数量保存对应真实截图，不设最多三张限制 | 原文件内的源时间位置 |
| 摄像头 | 实时 | 最新帧、公平调度、有界在途任务 | 保留现有连续/事件录像策略，保存工作异步化 | 已封口录像及其片内偏移 |

### 3.1 文件身份与所有权

- 用文件内容 SHA-256 作为 asset_key；异步分块计算，不在 GUI 线程散列大文件。规范路径、大小、修改时间作为缓存校验信息，不能代替内容身份。
- 分析前后校验文件状态；分析中内容改变就中止该版本任务，重新建立身份，不能把新旧内容混在一起。
- 路径变化但内容相同可复用分析；同一路径替换内容须新建资产。缺失源文件展示“原视频不可用”，支持重新定位并核验内容。
- 资产类型区分 external_source 与 managed_recording。删除事件、清理截图或将来的空间回收不能删除 external_source。
- 同一源文件在多通道使用，共享资产及分析结果，通道关系单独记录；不按通道复制事件截图。预览框仍按各自源时间显示。

### 3.2 源时间与帧契约

新增帧/结果元信息：channelId、sourceKind、assetKey、sourceGeneration、frameSequence、sourcePtsMs、loopIndex、captureMonotonicMs；直播另保留实际采集时间。

- sourcePtsMs 是原文件内的媒体位置，不是程序已经运行的时长，也不是循环次数乘时长。
- 明确 EOF / seek / 换源通知；跨代次的旧推理结果丢弃，不把文件尾与下一轮文件头拼成一个事件。
- VFR 文件优先使用有效解码时间戳；若当前 VideoCapture 无法提供可信的源时间映射，再为文件分析引入时间戳明确的解码适配器。不能无条件用帧号除 FPS 冒充准确时间。
- 原文件无可靠拍摄时间时，界面显示“源位置 00:12.500”和“分析时间”，不虚构实际拍摄日期。

### 3.3 一次分析、事件合并与去重

- analysis_key = hash(asset_key + model_hash + 预处理/后处理版本 + 阈值 + 抽样策略 + 事件合并参数)。后端作为运行记录保存；若结果差异超过容限，不能无条件视为同一配置。
- 本地文件分析与循环预览解耦。默认按源时间每 500 ms 取一个确定样本作为起点；文件任务按需解码下一样本，不积压整部视频到内存。处理慢时延长分析耗时，不丢未分析样本后误报“已完成”。此策略可能漏掉短暂目标，界面需显示采样间隔。
- 以首次阳性样本开始事件；持续阳性合并，连续无阳性超过 3 秒源时间后结束。实际事件结束位置取最后阳性时间；回放可默认提前 2 秒定位。数值为待真实素材验证的初始参数。
- 3 秒合并间隔内再次出现归入同一事件；超过间隔的新出现保留为另一事件。EOF 封口当前事件，不等待固定 60 秒、不连接下一轮开头。
- event_key = hash(analysis_key + 首个阳性样本序号 + 事件类型)。处理顺序确定；数据库唯一约束和事务完成最终幂等，不能只靠内存 set 或墙钟冷却。
- 将分析进度、活跃事件状态、已提交样本位置一起持久化。中断后从安全检查点恢复，重复执行覆盖已有键，不重复保存。
- 相同文件/配置已完成时，循环预览直接复用事件和检测结果；不重跑模型、不写新事件、不写新截图。缓存框仅在对应源时间附近显示，过期则隐藏。
- 模型/阈值变化或显式重新分析生成新分析版本；默认查询显示选中的版本，历史版本可查看，不把多个版本叠成重复报警。
- 用户进一步确认：每个去重事件保存一张代表截图，事件数量不限。不按循环次数重复保存。摄像头旧三图契约单独兼容。

## 4. GPU 接入策略

首选试验：保持 Qt/MinGW 界面，新增 ONNX Runtime CUDA 推理适配层，通过 C API 和受控 DLL 加载接入。保留 OpenCV CPU 适配层用于降级和结果对照。

- 先做独立小程序：锁定一个正式 ORT 版本及对应 CUDA/cuDNN/VC 运行依赖，记录版本和校验值，再用当前 yolov8n.onnx 完成真实输入推理。
- C API 方案的 MinGW 兼容性必须实测；不直接混用 MSVC 与 MinGW 的 C++ 对象/运行库。若此路线失败，备选为 MSVC 编译的独立 GPU 推理进程，通过有界 IPC 传数据，Qt 项目保留现有工具链。
- DLL 从应用明确的运行库目录加载；验证干净进程环境中的可用性，不靠开发机全局 PATH。GPU 依赖、模型和二进制不提交 Git。
- 日志同时记录请求后端、实际执行后端、模型版本、预热时间、推理 P50/P95、显存占用。用 ORT profiling 核实核心节点在 CUDA 上执行，GPU 利用率仅为辅助证据。
- 自动模式：GPU 初始化或执行失败时，安全销毁失效会话并降级 CPU，显示原因；GPU 严格测试模式：任何回退判定失败，禁止静默回退冒充成功。
- 初期 FP32、batch=1、复用一个模型会话。现有固定输入为 [1,3,640,640]，不能直接拼四帧做 batch=4；动态批处理/FP16 另行验证收益和精度后再做。
- 一个调度器公平服务四路；摄像头每路最多一张待处理最新帧，文件分析每任务只按需生产下一样本。初期全局一个执行中任务，实测后再决定是否提高并发。
- 保持现有预处理和输出解析进行 CPU/GPU 一致性对照，防止同时改变检测语义掩盖后端问题。NMS 等算法改动单独验证。
- 目前只完成能力探测，没有安装新 GPU 依赖，也没有修改程序后端。

## 5. GUI 与持久化改造

引入 StorageWorker，负责媒体清单、截图编码、事件索引、入库、失败重试；数据库连接在该工作线程内创建和销毁，不能传入 GUI 的 QSqlDatabase 连接直接使用。

- MainWidget 只提交轻量请求、接收保存状态和刷新结果。自动恢复和相关审计写入也迁出 GUI。
- 去掉“刚编码 PNG/Base64 立即重新解码”的正常保存路径。恢复清单保留版本号与文件引用；可恢复性不因优化丢失。
- 使用有界请求队列与磁盘待办；文件分析在持久化追不上时暂停生产下一任务，摄像头保存请求在后台可靠落盘。不能无限堆积大 QImage，也不能静默丢事件。
- 定义处理中、待保存、已完成、失败可重试；成功状态必须在媒体/索引达到持久化边界后发布。
- 关闭时先停接收与生产，再收尾工作线程；仍在处理的任务落盘后恢复。GUI 不同步等待长 SQL/图片编码；保留现有录像封口语义。
- GPU 加速不涉及录像硬件编码；本次性能报告必须区分推理收益与编码/存储成本。

## 6. 数据结构与兼容性

拟新增结构，最终字段与迁移 SQL 在实现阶段据当前真实 schema 核对：

| 结构 | 核心内容与约束 |
| --- | --- |
| media_asset | asset_key UNIQUE、外部源/托管录像类型、源时长、文件大小 |
| media_asset_location | asset_id、规范路径、内容校验信息；支持移动/多个相同内容位置 |
| media_analysis | analysis_key UNIQUE、asset_id、模型/策略版本、状态、检查点、当前活跃事件状态 |
| media_analysis_channel | analysis_id 与 channel_id 关联，复用结果而非复制媒体 |
| source_event | event_key UNIQUE、analysis_id、start_ms、end_ms、类型、置信度、保存状态 |
| source_event_image | event_id、样本序号、source_pts_ms、截图路径；UNIQUE(event_id, sample_index) |

- 文件事件采用独立索引结构，不把每个事件伪造为新的 video 录像行；摄像头旧表与 event_media_link 保留。
- 统一回放入口返回 PlaybackTarget：媒体类型、路径、源偏移、可选事件范围；文件走原文件定位，摄像头走现有 video_id 及片内偏移。
- 文件事件的图片使用源偏移，不复用“capturedAt + offset”推算拍摄日期的旧语义。列表标清文件分析/实时监控及对应时间。
- 旧录像继续可查询回放，旧恢复 JSON 继续可读取；新清单使用版本化解析。
- 迁移只新增结构和必要配置，提供 SQLite、隔离 MySQL 演练及升级前备份步骤。生产迁移尚未授权执行；准备好具体脚本和验证证据后才进入确认环节。
- 旧版程序不理解新索引；回退保留新增表/数据并切回旧程序，不做破坏性降级，不宣称旧版支持新事件。

## 7. 实施顺序与交付门槛

1. 基线复现：真实有人短片循环四路，统计检测关闭/CPU 检测/事件封口/恢复重试下的 GUI 心跳、CPU、帧率、文件数量与字节增长。先确认当前二进制对应源码。
2. GPU 可行性试验：固定输入真实推理、CPU/GPU 输出对照、实际 CUDA 节点证据、干净环境部署；成功后再合入适配层。
3. 存储异步化：迁移 GUI 上的编码/SQL/恢复，增加慢存储、数据库断开、退出恢复测试。
4. 文件身份与策略：源类型分流、时间戳元信息、停止文件重新编码；索引功能完成前不作为完整版本交付。
5. 文件事件分析：确定抽样、事件合并、持久化幂等、EOF/断点恢复、三图数量兼容、原视频回放及源文件缺失提示。
6. 接入 GPU 公平调度、配置和实际后端状态；进行真实四路长于事件周期的集成测试。
7. 按 scripts/build-and-test.ps1 完整回归，更新数据契约与验收记录；生成匹配源码指纹的发布包。准备生产迁移方案后再确认执行。

每步可独立验证。开始实施后先复现再修改；本次规划不直接变更运行中的通道配置或业务数据。

## 8. 验收矩阵与候选指标

| 场景 | 必须验证的结果 |
| --- | --- |
| 同一短文件循环 20 次，四通道共享 | 完成分析后事件/截图数量稳定，普通/事件 MP4 新增均为 0；四通道关系保留 |
| 重启、开关检测、移动文件、重复添加 | 内容与配置相同复用分析，不重复保存；原视频 hash 不变 |
| 相同路径替换不同内容 | 新资产与新分析，不错误套用旧结果 |
| 人持续出现、短暂消失、再次出现、EOF | 按源时间合并/分离，尾部独立结束，下一轮不开新事件 |
| 分析中断与持久化失败 | 检查点恢复、不假报已完成、唯一键防重复；旧恢复清单兼容 |
| 源文件删除/重定位、VFR、超短片 | 缺失提示准确；回放源偏移可信；不足三图不伪造 |
| 删除文件事件/空间维护 | 只作用于系统生成的索引和截图，原视频不被删除 |
| 摄像头同样的人稍后再出现 | 仍能产生真实的新事件，不被文件内容去重机制误伤 |
| GPU 缺依赖/不可用/执行错误 | 自动模式明确降级，严格模式失败；预览保持可操作 |
| 四路真实有人视频 + 集中事件保存 | 至少测 10 分钟，覆盖完整事件保存和恢复周期；分别报告 GUI/推理/存储指标 |

候选性能门槛（需在固定素材与电源模式下验证，不是已达成承诺）：25 FPS 输入时预览每路至少 20 FPS；20 ms GUI 心跳 P95 不超过 50 ms、最大间隔小于 200 ms；GPU 同输入预热后推理 P95 低于 CPU 基线；队列长度有硬上限，内存/显存与待办量无无故持续增长。测试记录具体分辨率、编码、模型、实际后端、推理采样频率和处理样本数。

“GPU 推理通过”“文件去重通过”“真实摄像头通过”“长稳通过”分别记录，不互相替代。
